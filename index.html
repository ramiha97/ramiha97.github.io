Overview

The platform started as a monolithic prototype. After the company raised funding I led the redesign into 6 event-driven microservices on EKS, splitting work into two paths: synchronous REST endpoints for operations that must answer immediately, and asynchronous workers for anything heavy — with results pushed back over WebSocket rather than making clients poll.

Core capabilities

Synchronous API flows

REST endpoints for immediate request/response operations, served from Redis where the access pattern allows it.

Asynchronous job processing

Long-running work is dispatched to background workers so the API acknowledges immediately instead of holding a connection open.

Real-time client updates

WebSocket channels deliver live job status and final results, removing polling load from the API tier.

Storage by access pattern

Each datastore was chosen against a specific access pattern rather than defaulting to one engine for everything.

Architecture

  1. Client Layer: REST for synchronous operations, WebSocket for live job status.
  2. API Layer: FastAPI services on EKS validate requests and either serve directly or enqueue a job.
  3. Data Layer: DynamoDB for single-key, high-volume access (job state, sessions); Aurora PostgreSQL for relational and transactional workloads.
  4. Search Layer: OpenSearch vector indexing for semantic and similarity-driven retrieval.
  5. Async Layer: background workers process long-running jobs and publish results back to the waiting client.
  6. Caching Layer: ElastiCache (Redis) fronts hot read paths, absorbing the majority of read traffic.
  7. Media Layer: S3 + CloudFront for global edge delivery of images and static assets.
  8. Operations: IRSA per workload, private-subnet isolation, CloudWatch dashboards and alarms.

Engineering decisions

  • Split sync and async paths so slow work can never occupy a request thread or a client connection.
  • Chose DynamoDB, Aurora and OpenSearch per access pattern, accepting the cost of operating three engines in exchange for predictable performance on each.
  • Pushed results over WebSocket instead of client polling, cutting redundant read traffic against the API tier.
  • Put Redis in front of the hottest read paths, taking DB load down ~80% at an 88% hit rate.
  • Moved static media to CloudFront so image delivery never touched application compute.
  • Scoped one IAM role per workload via IRSA rather than sharing a node-level role.

Overview

A serverless scraping and ingestion platform built for cost efficiency and replayability. Compute runs only when triggered, every raw payload is written to S3 before any transformation, and normalization happens asynchronously downstream. That separation means a bug in the transform logic is never data loss — it is a reprocessing job.

How it works

1) Event-driven scraping

EventBridge schedules and Lambda executes, so there is no always-on fleet idling between jobs.

2) Raw data lake

Every original response lands in S3 untouched — the source of truth for reprocessing, audit, and debugging.

3) Async processing

SQS decouples collection from processing; workers validate, clean, deduplicate and enrich without ever blocking the scrapers.

4) App-ready storage

Normalized records are written to DynamoDB for scalable key access and Aurora Serverless for relational queries.

Reliability model

  • Retries with backoff on transient source failures.
  • Dead-letter queues capture poison records instead of stalling the queue; DLQ depth is alarmed.
  • Deduplication on record identity so re-delivery never produces duplicates downstream.
  • Full replay from the S3 raw lake — transform logic can change and history can be rebuilt.
  • CloudWatch logs, metrics and alarms covering invocation errors, queue depth, and freshness.

Why serverless

Scraping load is bursty and idle most of the time — the worst possible shape for always-on instances. Event-driven Lambda means paying only for execution, which is where the cost advantage over an equivalent EC2 fleet comes from. The trade-off accepted was per-invocation limits and cold starts, neither of which matters for background ingestion.

The problem

Summarizing large documents naively means sending everything to the model: expensive, slow, and worse — long inputs contain heavy redundancy, so much of that spend buys nothing. The fix was not a better prompt. It was not sending redundant text in the first place.

How it works

1) Async job submission

The client posts the payload, job state is persisted, and the task is dispatched to background workers — the API acknowledges immediately regardless of document size.

2) Embeddings + K-Means

Segments are embedded with Amazon Titan Embeddings and grouped by K-Means, so semantically similar passages collapse into shared clusters.

3) Representative selection

One representative segment per cluster moves forward. Redundancy is dropped while topical coverage is preserved — this is where the token reduction comes from.

4) Inference + delivery

The reduced set goes to an LLM on Amazon Bedrock, and the finished summary is pushed to the client over WebSocket.

Production architecture

  1. Client Layer: submits a request and gets an immediate acknowledgment with a job ID.
  2. API Layer: validates input, persists job metadata, dispatches to workers.
  3. Async Layer: workers run embedding, clustering, selection, and inference.
  4. AI Layer: Titan Embeddings for vectors, Bedrock for generation.
  5. Data Layer: job state, inputs and outputs stored for traceability and replay.
  6. Delivery Layer: WebSocket push on completion — no client polling.

Engineering decisions

  • Made the whole flow asynchronous — inference latency is unpredictable and should never sit inside a request/response cycle.
  • Attacked cost before the model call rather than after; reducing input is the only lever that scales linearly with spend.
  • Used clustering rather than truncation, so long documents lose redundancy instead of losing their ending.
  • Persisted job state at every stage so a failed run resumes instead of restarting from the client.
  • Pushed over WebSocket rather than polling, which would have multiplied read load per in-flight job.

Overview

Most backend systems fail gracefully because their dependencies are software. This one controls real hardware — devices that overheat, drop USB connections, run out of battery, and hang. The engineering problem was building an orchestration layer that treats an unreliable physical fleet as a dependable resource pool.

Core capabilities

Parallel device execution

Dozens of real Android devices run simultaneously, turning a hardware cluster into a schedulable pool.

Async task processing

Queue-driven dispatch means long-running device workflows never block the control plane.

Real-time control & monitoring

Device state, execution logs, and task progress are tracked live for full operational visibility.

Health-aware task routing

Tasks are assigned based on device availability, health, and historical performance — unhealthy devices are drained rather than retried into.

Architecture

  1. Device Layer: physical Android devices exposed for remote access and control via STF.
  2. Control Layer: backend services issue ADB commands, execute workflows, and collect telemetry.
  3. Queue Layer: async job queues distribute tasks across the fleet and decouple submission from execution.
  4. Processing Layer: workers handle execution, retries, and workflow coordination.
  5. Data Layer: device logs, activity history, and execution records stored for traceability and analytics.
  6. Reliability Layer: continuous health checks, automatic recovery, and structured logging keep the fleet running unattended.

Outcome

A production SW/HW system that runs unattended around the clock, executing automation workflows at scale and collecting structured data with full traceability — treating an inherently unreliable physical fleet as a reliable service.

Production Face Recognition Platform

Real-time face search combining GPU embedding extraction, OpenSearch vector retrieval, S3 media, and PostgreSQL metadata.

Overview

A face recognition platform where the client sends an image, the system extracts a facial embedding, runs approximate nearest-neighbour search against stored vectors in Amazon OpenSearch, then assembles the response from the matched image in S3 and structured metadata in PostgreSQL — designed for low-latency retrieval at index scale.

Recognition pipeline

1) Client image request

The client uploads an image to the API, starting the recognition workflow in real time.

2) Embedding extraction

An InsightFace model on GPU infrastructure detects the face and produces its embedding vector.

3) Vector similarity search

The query vector is matched against the OpenSearch index to find the nearest neighbours and their identity references.

4) Media + metadata assembly

The matched image is fetched from S3 and enriched with PostgreSQL metadata into a single API response.

Architecture

  1. Client Layer: image request for real-time identification.
  2. Inference Layer: GPU-backed model extracts the embedding.
  3. Vector Search Layer: OpenSearch indexes embeddings for approximate nearest-neighbour retrieval.
  4. Object Storage: matched media retrieved from S3 by identity reference.
  5. Metadata Layer: PostgreSQL holds structured identity and contextual data.
  6. API Layer: combines all three into one response.

Engineering decisions

  • Separated vector search, object storage, and relational metadata into three specialized stores rather than forcing one engine to do all three badly.
  • Used approximate rather than exact nearest-neighbour search, trading a small amount of recall for latency that stays flat as the index grows.
  • Kept GPU inference isolated from the API tier so model workload and request workload scale independently.
